# Common Issues

| Issue | Solution |
|---|---|
| `databricks: command not found` | Databricks CLI not installed. See [docs.databricks.com](https://docs.databricks.com/dev-tools/cli/install.html). |
| `Error: A new access token could not be retrieved...` | The CLI eagerly refreshes the default profile's token. Run `databricks auth login` to fix, or set `DATABRICKS_CONFIG_FILE` to an empty file for the scaffold call (auth is required for the next step anyway). |
| `Invalid project_name`: must match the pattern | Pattern is `^[a-z][a-z0-9_]{2,}$`: starts with a lowercase letter, then lowercase letters/digits/underscores, min 3 chars. Reject `My-Project`, `1foo`, `ab`. |
| Output directory not empty | `bundle init` refuses to overwrite. Pick an empty path or have the user move/remove existing files. |
| `Error: template path does not contain databricks_template_schema.json` | Wrong source path. The schema must be at the root of the template repo. Use the git URL form if the local-path resolution is uncertain. |
| Genie Code: `databricks --version` returns nothing | Expected — the Genie Code CLI wrapper doesn't expose `--version`. Skip the version check and proceed; surface `bundle init` errors if anything is wrong. |
| Workspace UI Deployments panel doesn't appear on the bundle | Bundle wasn't created inside a Git folder. The workspace UI only surfaces the Deployments panel for bundles under Git folders. Move the scaffold into a Git folder, or use the CLI to deploy (`databricks bundle deploy -t dev`). |
| `Invalid usage_policy_id` / pattern mismatch at init | The serverless usage policy ID must be a UUID (copy it from the workspace under Settings → Compute → Serverless usage policies → Manage, or from `create_usage_policy.sh` output) or blank. |
| Deploy fails with a permission error on `budget_policy_id` | The deploying identity lacks the **User** role on the serverless usage policy. Grant it on the policy's Permissions tab (Settings → Compute → Serverless usage policies → Manage) to developers and the staging/prod service principals. |
| Deploy fails: budget policy not found | The policy ID belongs to another account or has a typo. Re-check `variables.usage_policy_id` (and per-target overrides) in `databricks.yml`. |
| Serverless usage stopped being tagged, deploys succeed | The policy was deleted. Resources keep its ID, but it applies no tags. Create a new policy and wire it in with `scripts/enable_usage_policy.py`. |
| Serverless usage has no `project` tag in `system.billing.usage` | No usage policy is attached. The `budget_policy_id` lines are still commented out, or the policy lacks the `project`/`environment` tags. Tags aren't retroactive, and billing rows can lag by a few hours. |
| Lakebase memory silently does nothing; App logs show `permission denied for schema public` | The App's service principal can connect to Lakebase but lacks `CREATE ON SCHEMA public`, so the memory tables are never created and the agent runs without memory. Once, as the database owner: `GRANT USAGE, CREATE ON SCHEMA public TO "<app-sp-client-id>";` (client id from `databricks apps get <app-name>`). Section 2e of the generated `docs/setup.md` has the details. |
| `project slug already exists in the workspace` when deploying the Lakebase memory project | A deleted Lakebase project keeps its slug reserved for 7 days of soft-delete retention, even though `databricks postgres list-projects` no longer shows it. Purge it early with `databricks api delete "/api/2.0/postgres/projects/<project>-memory?purge=true"`, or wait for its `purge_time`. See Troubleshooting in the generated `docs/setup.md`. |
